# Botfolio beta
Independent Secret J product, sharing only the existing session and CV API. No legacy Botfolio backend/UI/API reused.
- /botfolio.html: authenticated owner workspace; load existing PDF/DOCX from Neon using existing CV API and parse locally; review text before indexing. Alternative file and manual paste. Up to five bots per owner, isolated snapshots; create private, explicitly publish/unpublish, delete.
- /botfolio-chat.html?id=UUID: public chat; iframe HTML and shareable link. No public raw CV endpoint. Browser-session history only. Public bot metadata is limited to name and headline.
- RAG: 650-character chunks with 70 overlap, multilingual BGE-M3 vectors stored in per-bot JSONB; cosine top four retrieval; GPT-OSS 120B (`openai/gpt-oss-120b`) via Groq's HTTPS chat-completions endpoint; Cloudflare runs BGE-M3 only. Existing indexed CVs need no re-indexing. On Workers use `BOTFOLIO_AI`; on Node/Vercel optionally use restricted `BOTFOLIO_CF_ACCOUNT_ID` and `BOTFOLIO_CF_API_TOKEN` for BGE-M3 REST inference. Supply the existing server-only `GROQ_API_KEY` on each runtime; GitHub Actions secrets are not automatically Vercel variables. Never expose keys to the browser. Prompt grounding reduces, but cannot eliminate, hallucinations or prompt injection.
- Migration 013_botfolio.sql creates only two new tables, RLS enabled, public grants revoked; user deletion cascades. Apply migration to the existing Secret J DB before release.
- Pilot limits: 5 bots/user, 5 indexing attempts/user/day, 15 chats/IP/day, 20 chats/bot/day, 1800 estimated neurons/day across Botfolio. The budget uses conservative estimates and charges before calls; Cloudflare account usage is shared with research, and only the Free plan prevents paid overage. Not live billing telemetry. UTC reset. Limit may constrain chats substantially during pilot; no paid fallback.
- Migration 014 adds only a private singleton rolling-24-hour Groq reservation ledger. Botfolio reserves conservatively by UTF-8 prompt bytes plus overhead and 400 completion tokens, then reconciles with reported total usage on success; failed attempts retain reservations. Botfolio has two simultaneous hard local caps: 900 Groq request attempts and 120,000 accounted tokens per rolling 24 hours across all users and both hosts. The first exhausted cap blocks additional calls. Job Hunter retains its existing request limits (up to 60 emergency Groq attempts), with 75K rolling tokens; the 120K Botfolio token cap preserves 5K estimated shared headroom within the published 200K token quota. Provider quotas may stop traffic sooner. Provider/account rate limits still apply, including 8K TPM and 30 RPM; 429 is handled without fallback or retries. Cloudflare's 1,800 estimated neurons/day is now embeddings only. Existing per-user, bot and IP quotas stay unchanged. A bounded ten-minute exact question/history cache in each process avoids repeating both AI calls for the same published portfolio revision; it is not persistent or approximate semantic caching. Keep provider accounts on free plans; no paid tier is selected by the code.
- No account, job, alert, or research logic changed. Only Botfolio entry points, allowlisted post-login redirect, new API route and binding, and additive migration. CI uses mocked inference; verify actual inference, indexing, publish, iframe and quotas before production claims.

- Admin Console → Botfolio AI Usage uses the existing authenticated admin API, reads aggregate Botfolio ledger data only, reports rolling 24-hour Groq attempts, observed outcomes, provider-reported and unverified/reserved tokens, local remaining requests and tokens, and UTC-day embedding estimates and per-bot/IP limits. No provider calls on refresh. Old ledger entries lacking outcome metadata remain unclassified. Model configuration is host-specific, not a health probe; usage is not shared-account telemetry. No new tables. The 900-request and 120K-token limits are enforced atomically by the existing ledger; failed attempts count and cache hits do not.

- Admin reset display: generation requests and accounted tokens expire individually 24 hours after reservation. Show next expiry and final expiry if no new requests, both explicitly in Africa/Cairo time, with time remaining at refresh. Embeddings and daily chat/index counters reset at midnight UTC (02:00 Cairo in winter, 03:00 in summer). Actual shared Groq provider reset is separate and not inferred from local counters.

- Provider reset display uses the most recent recorded Groq RPD/TPM header observations from either product. Capture timing only on existing provider calls, store in existing reservation JSON, no probe, new schema or quota change. Groq TPD reset remains unreported; past observations are labeled accordingly.

- Scope and token efficiency: local deterministic greetings and clear off-topic/prompt-extraction/personal queries bypass both providers. Other questions use the existing query embedding, with a conservative 0.28 cosine floor for non-explicit professional queries; the floor is a heuristic, not a calibrated classifier. Retrieve up to two chunks for focused questions and three for broad professional questions, at most 1,800 evidence characters. Only a previous user question (up to 240 characters) may be included for contextual follow-ups; assistant answers are never treated as evidence. Exact refusal markers become localized fixed replies. The 400 completion-token ceiling remains to avoid reasoning-model truncation; prompt targets short answers. No new model, provider, schema or global budget change. Existing chat attempt quotas still count rejected requests. Test with actual multilingual traffic before tuning the heuristic.

- Qwen 3.8 27B (`qwen/qwen3.8-27b`) is the sole Botfolio fallback. Existing GROQ_API_KEY, same endpoint, same strict RAG prompt and retrieved evidence; no second embedding. Primary GPT-OSS is preferred until a local quota, provider failure or invalid response blocks it, then one Qwen attempt is made. Qwen reasoning disabled; separate 900 attempts and 190,000 reserved/reconciled tokens per rolling 24 hours, leaving 10K headroom against the published 200K model allowance. Both providers are actually Groq models: organization limits, model access and any shared provider restrictions still apply. Existing ledger JSON entries without a model tag are treated as GPT-OSS; no migration or reset. Rate-limited models have a 60-second local shared cooldown (recorded on existing ledger). Admin telemetry separates the models. No changes to Job Hunter or existing GPT-OSS budgets. No paid service tier requested; verify the Groq organization is on Free and model quotas are available before relying on 310K combined local allocation.
